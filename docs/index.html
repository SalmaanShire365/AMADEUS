Retrieval, as it actually ran

What the evaluation settled

A harness scores retrieval against questions whose correct answer file is already known, reporting recall@k and mean reciprocal rank. Four changes were tried against the baseline. Three of them made things worse.

Excluding test files from the index

Test files were 44% of the corpus and were outranking the code they test. One question about heartbeat staleness returned eight test files and zero implementation.

MRR 0.688 → 0.812
recall@5 0.750 → 0.938

Aligning chunk boundaries to lines

The chunker was slicing functions mid-token, which looked like the obvious culprit. After the fix, retrieval returned the same eight chunks at the same distances to four decimal places.

MRR 0.812 → 0.812
no measurable change

Blending keyword overlap into the ranking

Swept across weights from 0.02 to 0.30. Common tokens appear in nearly every file, so the boost was close to uniform noise.

MRR 0.812 → 0.729
degraded at every weight

Weighting those keywords by rarity

If common tokens were the problem, rarity weighting should have fixed it. It didn't — term presence across a 1,500-character chunk carries little signal however it's weighted.

MRR 0.812 → 0.750
degraded at every weight
