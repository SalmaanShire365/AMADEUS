01 / Status

Where the project actually is.

A working retrieval pipeline with a measured baseline, one known failure mode, and a lot of unbuilt roadmap. Stated plainly so the rest of the page can be read honestly.

Working

  • Repository indexing with structure-aware chunking
  • Local embeddings via Ollama, vectors in SQLite
  • Incremental re-indexing by file hash
  • Grounded answers with file:line citations
  • Evaluation harness reporting recall@k and MRR
  • Tiered model routing, 1.5B through 8B

Partly working

  • Ranking — the right file is retrieved 94% of the time but ranked first only half the time
  • Multi-concept questions collapse to whichever term dominates
  • Relevance filtering controls context width, not topicality
  • The benchmark is eight questions; too small to detect small effects

Not started

  • Symbol and call-graph indexing
  • Repository knowledge graph
  • Iterative, agent-driven retrieval
  • Change-impact analysis
  • Patch generation and verification

03 / Evaluation

Four changes tried. Three made it worse.

The harness scores retrieval against questions whose correct answer file is already known. Current baseline: recall@1 0.500, recall@5 0.938, MRR 0.812. The interesting part is what didn't work.

Worked

Excluding test files from the index

MRR 0.688 → 0.812

Test files were 44% of the corpus and outranked the code they test. One question about heartbeat staleness returned eight test files and zero implementation. Recall@5 went 0.750 → 0.938.

No effect

Aligning chunk boundaries to lines

MRR 0.812 → 0.812

The chunker was slicing functions mid-token, which looked like the obvious culprit. After the fix, retrieval returned the same eight chunks at the same distances to four decimal places.

Worse

Blending keyword overlap into ranking

MRR 0.812 → 0.729

Swept from weight 0.02 to 0.30. Common tokens appear in nearly every file, so the boost was close to uniform noise.

Worse

Weighting those keywords by rarity

MRR 0.812 → 0.750

If common tokens were the problem, IDF weighting should have fixed it. It didn't. Term presence across a 1,500-character chunk carries little signal however it's weighted.

What that suggests: code retrieval isn't text retrieval with more scoring terms bolted on. The gains came from corpus quality, not ranking cleverness — which is the argument for indexing software structure next rather than tuning heuristics further.
04 / Build log

What actually happened, in order.

Kept honestly, including the parts that were stalled or wrong.

16 AUG 2026

A tracking ticket, and then nothing

Opened a work item for a retrieval evaluation harness and didn't touch it for eleven days. The pipeline existed on paper but had never been run end to end against a real index.

26 AUG 2026

First working retrieval

Got the pipeline running against its own source. Found that chunk boundaries were slicing functions mid-token and fixed them — which changed nothing at all. Swapping the prose-trained embedding model for a code-trained one was the change that actually moved rankings.

line-aligned chunking · jina-embeddings-v2-base-code · relative distance margin
26 AUG 2026

Absolute relevance thresholds don't work

Distance bands shift per question, so a fixed cutoff admits everything on one query and nothing on the next. Worse, an entirely off-topic question scored better than the tail of a legitimate one. Replaced with a margin measured from the closest match, and accepted that topicality isn't filterable at this layer.

29 AUG 2026

Indexed a real codebase

1,231 Go files from an open-source project, 19,979 chunks, sixteen minutes on a local GPU. Retrieval that had looked mediocre against a four-file corpus turned out to be good — there simply hadn't been correct answers to find before.

first end-to-end run at scale
29 AUG 2026

Evaluation harness and first baseline

Eight questions with hand-verified answer files, scored on recall@k and MRR. First number: recall@1 0.438, MRR 0.688. The failures in the table matched the ones already spotted by eye, which is what made the harness trustworthy.

29 AUG 2026

Test files were 44% of the corpus

Excluding them moved MRR to 0.812 and recall@5 to 0.938. Two reranking approaches tried afterwards both made things worse at every weight swept. Three experiments, one win — and knowing which was which took minutes instead of an afternoon.

recall@1 0.500 · recall@5 0.938 · MRR 0.812
6 SEP 2026

Grounded answers, verified end to end

Ran the full pipeline for the first time: question, retrieval, grounded prompt, local model. A 3B model ignored the citation instruction and invented a mechanism that wasn't in the retrieved code. An 8B model cited every claim and stayed inside its context. Grounded answers now default to the larger model.

generation was the bottleneck, not retrieval
OPEN

Multi-concept queries still collapse

Ask how convoys are stored in the database and you get convoy display code with no storage layer — even though asking about the storage layer alone returns it cleanly. The embedding averages the two concepts instead of requiring both. Unsolved.

05 / Roadmap

Where this is meant to go.

Each layer has to earn the next one with a measurable result. Everything past Phase 1 is a plan rather than a commitment — the point of writing it down is to have something specific to be wrong about.

PHASE 0

Reliable local retrieval

Indexing, chunking, filtering, and a reproducible benchmark. Mostly done; the benchmark needs to grow before smaller effects are detectable.

  • Repository ingestion and incremental re-indexing
  • Local embeddings, SQLite vector storage
  • Recall@k and MRR evaluation harness
Current
PHASE 1

Code-aware indexing

Stop treating source as anonymous text. The evaluation already points this way: corpus structure mattered more than any ranking heuristic tried so far.

  • Functions, types, interfaces, packages
  • Definitions and references
  • Imports and call relationships
  • Implementation ↔ test linkage
Next
PHASE 2

Repository knowledge graph

Connect retrieved chunks into something navigable, so a question can be answered by traversal rather than nearest-neighbour alone.

  • Call-graph traversal
  • Dependency and blast-radius analysis
  • Graph-aware reranking
Planned
PHASE 3

Agentic investigation

Let the model decide what evidence it still needs instead of taking a single retrieval pass. This is also the most direct candidate fix for the multi-concept failure above.

  • Query decomposition
  • Iterative retrieval loops
  • Confidence and source attribution
Planned
PHASE 4

Engineering workflows

Move from explaining code to helping someone operate on it.

  • ask — understand a behaviour
  • investigate — diagnose a problem
  • impact — estimate blast radius
  • Reasoning over commit history
Future
PHASE 5

Verified code changes

Propose changes, run the tests, iterate on failures — with the diff and its evidence always reviewable by a person.

  • Patch generation
  • Test execution and failure-driven iteration
  • Diff and evidence review
Long-term
PHASE 6

Private deployment

Package it for organisations that need codebase intelligence without sending source to an external service.

  • On-prem and air-gapped options
  • IDE integration
  • Auditability and access controls

06 / Thesis

Why retrieval is the interesting problem.

Getting a model to generate code is largely solved. Getting it the right code — the right history, the right dependencies, enough evidence to explain why a system behaves as it does — is not. A large repository holds implementation, tests, configuration and years of decisions that will never fit in one prompt.

A function isn't a paragraph. It has callers, callees, interfaces, implementations, tests and a history. If those relationships can be represented, retrieval becomes a deliberate investigation instead of a nearest-neighbour lookup. That's the bet this project is testing.

Onboarding

How does authentication work?

Trace controllers, services, external systems and tests into a walkthrough that cites its sources.

Debugging

Why is this timing out?

Investigate the relevant path, inspect error handling, and build a hypothesis from repository evidence.

Change impact

What breaks if I change this?

Traverse callers, interfaces and tests to estimate the blast radius before the change is made.

Legacy

What does this system do?

Turn years of unfamiliar code into architecture maps and dependency relationships.

Security

Where is authorization inconsistent?

Find semantically related implementations and surface suspicious differences for human review.

History

Why was this written this way?

Connect current code to prior implementations and the commits that changed it.

Speculative, and worth labelling as such: if the local-first constraint holds up, the audience is engineering organisations that can't send source code to an external service — finance, healthcare, defence, regulated software. That's a hypothesis about a market, formed from a project that currently has an eight-question benchmark. It's written down to be tested, not because it's established.
07 / Principles

Rules the project holds itself to.

Local first

Source code shouldn't need to leave the machine for core functionality.

Evidence first

Every answer points back to concrete files, symbols and lines.

Measure everything

Retrieval changes get evaluated, not assumed to be improvements. Three of the first four weren't.

Structure over tricks

Prefer understanding software relationships to stacking ranking heuristics.

Human in control

Investigation can be autonomous. Consequential changes stay reviewable.

Earn the complexity

Every new subsystem has to solve a demonstrated limitation of the last one.
